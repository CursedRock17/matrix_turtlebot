# Troubleshooting

Fast path: if the robot seems unresponsive at all, run the doctor first —
`ros2 run turtlebot4_custom_py preflight`. It checks the laptop↔robot link, the
discovery server, dock state, and `/odom` `/scan` `/battery_state` rates, and
drops a diagnostic bag in `claude_logs/`. Most of the tables below start there.

## Connectivity & discovery (robot ↔ laptop)

| Symptom | Cause | Fix |
|---|---|---|
| `ros2 topic list` shows only `/rosout` + `/parameter_events`, even shelled into the Pi | The Fast DDS discovery server isn't running on the Pi. `turtlebot4-setup` writes the service file but doesn't enable it, so it's a leftover process that dies on reboot | Make it persistent: enable `discovery.service` (or install one running `fastdds discovery -i 0 -l 0.0.0.0 -p 11811`), `sudo systemctl enable --now discovery`. Verify `ss -lunp \| grep 11811`. |
| Laptop sees no robot topics; nodes hang; nav2 spams `base_link to odom did not become available` | Robot is publishing nothing to the laptop — powered off/booting, `ROS_DISCOVERY_SERVER` unset, or discovery server down | `preflight`; power on and wait ~90 s; `ping 192.168.50.224`; re-source `turtlebot4_bringup/setup.bash`. It's a connection issue, not the code. |
| A nav node dead-ends at "Loaded location file" and hangs | Same as above — robot silent on the wire (`/odom`, `/dock_status` absent) | `preflight`; the `_wait_for_robot` guard now fails fast with an actionable message. |
| nav2 stuck at `Activating bt_navigator` / RViz: `navigate_to_pose action server is not available` | bt_navigator's BT action clients must be matched by a discovery server; over Wi-Fi to the Pi that stalls forever | Local discovery server on the laptop (`127.0.0.1:11888`), auto-started by `setup.bash`. Check `ss -lun \| grep 11888`; re-source if missing. |
| Everything broke after the robot's IP changed | The Pi is now `192.168.50.224` (was `.223`). The discovery script has no IP, but `ROS_DISCOVERY_SERVER` and docs do | Update the laptop `ROS_DISCOVERY_SERVER` in `setup.bash`. The Create 3 reaches the Pi over usb0 (`192.168.186.3`, unchanged), so its own config needs nothing. |

## Startup: localization & nav2

| Symptom | Cause | Fix |
|---|---|---|
| `CRITICAL FAILURE: SERVER map_server IS DOWN` (or `amcl IS DOWN`) ~4 s after `Managed nodes are active`; robot vanishes from RViz | The localization lifecycle manager's 4 s bond watchdog — a big map (first_floor, 2496×745 ≈ 1.86 MB) blocks map_server's executor past the heartbeat | Launch localization via `ros2 launch turtlebot4_bringup localization.launch.py` (our bond-disabled wrapper), NOT `turtlebot4_navigation`'s. |
| `Failed to activate global_costmap … transform base_link to map` → `Aborting bringup`; "have to run nav2 twice" | The global costmap needs the `map` frame, which AMCL only publishes after the nav node undocks and sets the initial pose | Start the nav node right after launching nav2 (don't wait for activation). `initial_transform_timeout: 600` in `nav2.config.yaml` lets it wait instead of aborting at 60 s. |
| nav2 hangs at "Waiting for service … get_state" | Discovery traffic not flowing | Verify the discovery server is reachable (`ping 192.168.50.224`) and kill stale ROS processes. |

## Navigation behaviour

| Symptom | Cause | Fix |
|---|---|---|
| Goals abort `Failed to make progress` / `getTransform … extrapolation into the future`; lidar spinning but `/scan` looks "stale" in RViz | Intermittent 1–2 s stalls in scan/tf/odom **delivery**, NOT clock skew (mean `/scan` age was 17 ms; it had 1.9 s gaps). From laptop CPU saturation and/or Wi-Fi | Reduce laptop load (`use_rviz:=false`, watch `htop`); long-term run nav2 on the Pi. The patrol loop holds instead of driving blind. |
| Robot drives but localization drifts or jumps | Time sync (laptop→Pi→Create 3 chrony chain) not converged | `ros2 topic delay /odom` (want 0.01–0.05 s); see [time_sync.md](./time_sync.md). |
| TF `extrapolation into the future` by only 50–260 ms + `collision_monitor: Robot to stop due to invalid source`, clustered at certain hallway spots | Wi-Fi AP roaming stalls all robot traffic ~0.1–2 s; nav2's default TF margins (0.1–0.3 s) were tighter than routine lag | `transform_tolerance: 0.5` everywhere + collision monitor `source_timeout: 1.5` (nav2.config.yaml, 2026-07-02). Map the roam spots: run `wifi_survey.py` **on the Pi** during a patrol — the `bssid` column changes exactly where roams happen. |
| `/scan` publishes fine (7 Hz) but nav is dead for ~30 min: `collision_monitor … timestamps differ … Ignoring the source`, TF `extrapolation into the past` | A robot-side clock diverged mid-run (seconds to minutes); chrony corrects by *slewing*, so nav2 rejects every scan until it converges | `makestep 1 -1` in the Pi's chrony.conf (steps instantly). The patrol loop now holds on stamp skew and says so. Cause hunt: `journalctl -u chrony` on the Pi — see [time_sync.md](./time_sync.md) case study. |
| Patrol ends with `Failed to dock for charging` — robot stops short of the dock | The Create 3's IR docking only works from ~1 m with the dock in view; nav2 can deliver the approach pose with enough error to miss that window. Worse (2026-07-02): a scan stall at the dock starved AMCL, all three *approach* navigations failed, and the old loop called `dock()` anyway from wherever the abort left it | The patrol loop retries docking (3×), holding for a usable `/scan` before each approach and only spending a `dock()` on an approach that succeeded (last attempt is a hail-mary). Survey `approach_pose` ~0.5–1 m squarely in front of the dock. |
| A single goal overruns and gets cancelled | Building-scale legs are long and slow | `GOAL_TIMEOUT_SEC` is 300 s; keep patrol legs short (the first_floor patrol is out-and-back so no leg is the full ~50 m). |
| Robot clips people's feet | The lidar CAN'T see feet — they're below its plane. It sees (and avoids, as normal dynamic obstacles) the **legs**; the toes just stick out ~15–20 cm past the shin it's avoiding. No lethal radius fixes that: covering toes needs ~0.37 m, and the post passage closes at >0.25 | Four-layer response (nav2.config.yaml): `robot_radius: 0.25` hard bubble (MPPI enforces it as collision), soft inflation (`0.5`), the `VirtualBumper` ring — within 0.45 m of anyone the robot slows to 30% **and beeps** (via `bump_to_cloud`) — and any actual contact becomes a ~10 s costmap obstacle so nav2 reroutes instead of retrying the path. `bump_to_cloud` is embedded in every nav node; it only needs starting by hand for manual RViz-goal sessions. |
| Robot sees a person, stops, but never plans around them ("won't create a new path") | Not a costmap-marking problem — their legs ARE marked as dynamic obstacles. With a big `robot_radius`, a person's leg carries a lethal disc so wide that passing them needs 2×radius of free corridor width; mid-corridor that can leave NO legal path, so the planner correctly reports none (bench, 2026-07-09 at 0.40) | Keep `robot_radius` at 0.25 — a person mid-corridor then needs only 0.5 m of free width to one side. If it still won't pass, the person is genuinely blocking a narrow spot; the robot waits them out (and beeps) by design. |
| Can't get back through the crossroads↔corridor passage (the way to the dock) | A REAL POST stands mid-opening at (31.9, −2.6), splitting the 1.55 m passage into two ~0.75 m halves — the narrowest gaps on the patrol route, tighter than the 80 cm doors. `robot_radius` 0.30 left only a 15 cm band and failed live (2026-07-09) | `robot_radius: 0.25` (25 cm band per half). This post is the building's binding constraint on the keep-out radius — do NOT erase it from the map (it's physical; that was mistakenly tried and reverted 2026-07-08) and don't raise the radius past 0.25 without re-testing this passage first. |
| Bumping into something doesn't make the robot replan around it | The costmap `bump_points` source has no publisher, so bumps only trigger the Create 3 firmware reflex (stop + back up) and nav2 retries the same path | The nav nodes (nav_to_node, nav_patrol_loop, patrol_with_llm) embed `bump_to_cloud` automatically after a `colcon build`; for MANUAL RViz-goal sessions run `ros2 run turtlebot4_custom_py bump_to_cloud` yourself. Verify the chain: press a bumper → `ros2 topic echo /hazard_detection` shows a BUMP → `/bump_points` grows a point → a red dot in the local costmap for ~10 s. |
| A doorway goal starts failing / planner won't enter a room it used to | The oversized `robot_radius` made that spot lethal — the waypoint is now within ~0.25 m of a wall, or the gap is narrower than ~0.5 m + tracking margin | Nudge the waypoint toward the room's open space (`survey_locations`), or measure the gap in the map; shrinking the radius below 0.25 is the last resort. |
| Robot won't leave the dock / "stuck on the dock" right after undocking | The undock zone is only ~0.5–0.6 m off the dock wall/structure. Two separate ways to poison it: `inflation_radius: 0.85` blanketed it in cost (field, 2026-07-09), and `robot_radius: 0.40` put the undock pose within noise of lethal (bench, same day) | Keep `robot_radius` at 0.25 and `inflation_radius` ≤ 0.5 — the undock pose then has ~0.3 m of lethal margin and zero inflation cost. The 0.45 m slowdown ring is speed-only and can't wedge it. |
| `Waiting for amcl_pose to be received` loops forever | AMCL has no laser scan — robot docked (lidar off) or silent | `ros2 topic hz /scan`; the nav nodes now spin the lidar up front, so rebuild + re-source if you still see this. |

## Lidar & sensors

| Symptom | Cause | Fix |
|---|---|---|
| `/scan` stops publishing while docked | The Create 3 powers the RPLIDAR off whenever it's docked — by design | Undock first (the nodes do), or `/start_motor`. This is NOT a hardware fault; docked bags showing `/scan` gaps with `is_docked=true` are expected. |
| Startup deadlocks — "waiting for costmap / lidar / initial pose", all circular | costmap ← scan ← lidar chicken-and-egg | `startup.py` calls `/start_motor` **first** (idempotent; never stops the lidar). The undock is only for the pose, not to wake the lidar. |
| Node fails ~10 s after undock with "no scan" | Lidar didn't restart on undock (known redock issue) | The node retries `/start_motor` automatically; power-cycle the robot if `/scan` stays silent. |
| `turtlebot4.service` is enabled and running but there's no `/scan` AND no `/start_motor` service ("No start_motor service found to start the lidar with") | The rplidar node inside the Pi's bringup died or never started — the service being green doesn't mean its composed nodes are alive. Distinct from the docked-lidar-off case (no `/start_motor` = node gone, not motor stopped) | Workaround: on the Pi `ros2 launch turtlebot4_bringup rplidar.launch.py` in its own terminal. Diagnose: `journalctl -u turtlebot4 -b \| grep -iE "rplidar\|died\|error"` and `dmesg -T \| grep -iE "usb\|cp210"` (the RPLIDAR is USB-serial; a USB drop kills the node). First seen 2026-07-02. |
| `/scan` freezes mid-run but `/odom`/TF keep flowing (collision_monitor skew grows 1 s per s; TF buffer still advancing) | The rplidar node/USB died again — this is a **lidar** failure, NOT the network wedge (a wedge stops *everything* and `ping` hangs) | Restart the rplidar launch on the Pi. Happened 2026-07-02 ~11 min after a manual rplidar launch; check `dmesg` for a USB disconnect at that moment. A degraded rate (2 Hz instead of 7) beforehand is the same hardware complaining. |
| `/scan` behaves erratically (interleaved/jumping stamps, motor weirdness) after manually launching the lidar | TWO `rplidar_composition` nodes are up — the manual `rplidar.launch.py` plus the service's own node (it revived, or was never fully dead) — and they fight over the topic and the motor | `ros2 topic info /scan` — more than 1 publisher confirms it. Kill the manual launch or `sudo systemctl restart turtlebot4` on the Pi so exactly one owns the lidar. `preflight` now checks this (FAILs on 0 or ≥2 publishers). |
| Nav goal fails instantly when the robot is ON the dock (manual RViz goal, or a node that skipped the undock) | Docked, the robot center is only ~0.2 m from the wall — inside the 0.28 m virtual `robot_radius`, so the start pose is lethal. There is no nav2 "anti-keepout" (the keepout filter can only add cost, never subtract) | Undock first, always: dock/undock are Create 3 firmware motions that ignore costmaps (this is the designed escape from the dock's keep-out bubble). The nodes' `undock_and_localize` does this; for manual driving send `/undock` before the first goal. |

## Endurance & platform (Raspberry Pi)

| Symptom | Cause | Fix |
|---|---|---|
| After ~40–46 min, `/odom` + `/scan` stop, `/diagnostics` still looks healthy, `ping` hangs (not "unreachable") but the router shows the robot connected | Pi network stack wedged. (If **only** `/scan` stopped and `/odom` still flows, it's the rplidar node dying instead — see the Lidar table.) **Thermal, throttling, undervoltage, and memory are ruled out** (2026-07-02 endurance log: 53–64 °C, `throttled:0`, `undervolt:0`, flat 833 MB through a failure at 46 min uptime). Remaining suspects are time-based L3 events: DHCP lease renewal, Wi-Fi group rekey, or a `brcmfmac` driver wedge | When it happens, on the Pi: `journalctl -u systemd-networkd -u wpa_supplicant --since "-10 min"` and `networkctl status wlan0` (shows lease time). Long-term: less over-Wi-Fi traffic (nav2 on the Pi). |
| Discovery server / all topics vanish after a reboot | The discovery server was never enabled to auto-start | Persistent `discovery.service` — see the Connectivity table. |
| RPLIDAR (and the Pi's whole ROS stack) never comes up after boot | `turtlebot4.service` — the Pi's ROS bringup — found *disabled* (2026-07-01), same never-enabled disease as the discovery service | `ssh` in, `sudo systemctl enable --now turtlebot4.service`. After any `turtlebot4-setup` run, verify: `systemctl is-enabled turtlebot4 discovery`. |

## Debugging tips

- Full node logs live in `~/.ros/log/` even when a redirected terminal captured nothing — `ros2 run` buffers stdout. Read the file, not the terminal.
- When a run hangs silently, check the **previous** run's container log in `~/.ros/log/` — an earlier attempt often logged the error the wedged one didn't.
- Kill stale ROS processes between runs — orphan discovery servers hold port 11888 and leftover static TF publishers poison the real robot's TF tree.
- The laptop's local discovery server processes are named `fastdds.py` / `fast-discovery-server`, so check the port (`ss -lun | grep 11888`), not `pgrep`.
- `preflight` records a bag to `claude_logs/preflight_HHMMSS` every run — a failed startup always leaves the evidence.
